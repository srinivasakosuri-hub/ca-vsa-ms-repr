TemplateMs

A production-grade .NET 10 microservice template — Clean Architecture + Vertical Slice Architecture + Domain-Driven Design + WolverineFX

● .NET 10 ● WolverineFX ● Dapper ● ActiveMQ ● Scalar Docs ● Testcontainers ● Roslyn Analyzers ● 63 Architecture Tests

What problem does this solve?

Most microservice templates force you to pick between Clean Architecture (horizontal layers) and Vertical Slice Architecture (feature folders). TemplateMs uses both simultaneously:

  • Clean Architecture draws hard rings around Domain → Application → Infrastructure → Api. Nothing in an inner ring ever imports from an outer ring. Architecture tests enforce this at every build.
  • Vertical Slice Architecture organises code inside the Application ring by feature, not by type. Every file related to "create an order" lives in Features/Order/Commands/ — command, handler, validator, DTO, mapper, interfaces all together.
  • DDD provides the conceptual model: aggregates that protect invariants, domain events for loose coupling, a repository abstraction for persistence ignorance.
💡

The practical result: you find a feature by folder (vertical slice) and trust that it never corrupts another layer (clean architecture). Architecture tests make violations visible immediately — the build simply fails.

Why WolverineFX instead of MediatR?

MediatR is an in-process mediator — it dispatches messages and that's it. WolverineFX is a full messaging framework that happens to support in-process dispatch as well:

FeatureMediatRWolverineFX
In-process dispatch✓✓
Convention-based handlers (no interface)✗✓
Middleware pipeline (Before/After/OnException)Pipeline behavioursNative, richer
SQL Server durable inbox/outbox✗✓ via WolverineFx.SqlServer
External transport (AMQ, Rabbit, etc.)✗✓
Handler discoveryRequires IRequestHandler<T>Class ending in "Handler" + "Handle" method

Why Dapper instead of Entity Framework?

Dapper makes SQL explicit and reviewable. Every SQL string lives in TemplateMs.Sql as a const string. You can read, diff, and review the exact SQL that runs in production. Roslyn build analyzers prevent hardcoded database names or schema names from ever creeping in, keeping SQL environment-agnostic.

Domain Layer — TemplateMs.Domain

The innermost ring. Zero NuGet packages. Zero project references. Pure C# and the .NET BCL. The domain model captures the business vocabulary, rules, and behaviour of the Order system.

Everything in this project is designed to be tested without any infrastructure at all — no database, no file system, no HTTP. Domain tests run entirely in memory.

Entity Hierarchy — connecting the inheritance dots

BaseEntity               // int Id, equality by identity
  └─ BaseAuditableEntity  // + CreatedBy, CreatedAt, UpdatedBy, UpdatedAt
       └─ AggregateRoot   // + domain event tracking
            └─ Order      // sealed — the aggregate root for the Order context
       └─ OrderItem       // sealed — child entity, owned by Order
       └─ OrderItemAttribute // sealed — grandchild, owned by OrderItem

BaseEntity

public abstract class BaseEntity : IEntity
{
    public int Id { get; set; }

    // Equality is by Id — two Order instances with Id=5 are the same order.
    public override bool Equals(object? obj) { ... }
    public override int  GetHashCode() => Id.GetHashCode();
    public static bool operator ==(BaseEntity? left, BaseEntity? right) ...
}

Entity equality is by identity (the Id) not by value. Two Order objects with the same Id represent the same order, regardless of which properties are set.

BaseAuditableEntity

public abstract class BaseAuditableEntity : BaseEntity, IAuditableEntity
{
    public Guid CreatedBy   { get; set; }
    public DateTime CreatedAt { get; set; }
    public Guid UpdatedBy   { get; set; }
    public DateTime UpdatedAt { get; set; }

    // Helper — stamps both Created and Updated fields at once
    public void MarkAsCreated(Guid userId, DateTime? timestamp = null) ...
    public void MarkAsUpdated(Guid userId, DateTime? timestamp = null) ...
}

The audit fields use set (not private set) specifically to allow Dapper to hydrate them when mapping SQL results. This is the deliberate exception to the "no public setters" rule — Dapper needs column name → property name mapping to work.

AggregateRoot — domain event tracking

public abstract class AggregateRoot : BaseAuditableEntity
{
    private readonly List<DomainEvent> _domainEvents = [];

    // Read-only view for the UoW dispatcher
    public IReadOnlyList<DomainEvent> DomainEvents => _domainEvents.AsReadOnly();

    // Called from the aggregate's business methods to enqueue an event
    protected void AddDomainEvent(DomainEvent domainEvent) =>
        _domainEvents.Add(domainEvent);

    // Called by DapperUnitOfWork after dispatching events
    public void ClearDomainEvents() => _domainEvents.Clear();
}
🔑

Why AggregateRoot stores events instead of publishing them directly: The aggregate must not know about messaging infrastructure. It just records what happened. The Unit of Work dispatches those events after the SQL transaction commits, so there is no chance of publishing an event for a transaction that later rolled back.

Order Aggregate — the richest type in the codebase

Order is the only aggregate root in this template. It owns a collection of OrderItem, each of which owns a collection of OrderItemAttribute.

Factory method: Order.Create

public static Order Create(string customerName, DateTime orderDate, DateTime createdAt)
{
    if (string.IsNullOrWhiteSpace(customerName))
        throw new DomainException("CustomerName cannot be null or empty.");

    return new Order
    {
        CustomerName = customerName.Trim(),
        OrderDate    = orderDate,
        IsActive     = true,
        CreatedAt    = createdAt,
        UpdatedAt    = createdAt
    };
}

The factory method is the only way to create a valid Order. It enforces the invariant that CustomerName cannot be empty before the object exists. No validator can be forgotten because the domain enforces it unconditionally.

⚠️

Why doesn't Create raise OrderCreatedEvent? At the point Order.Create() is called, the order has no database Id yet. The event payload needs the Id. The handler calls repository.AddAsync(order) first (which INSERTs and sets order.Id), then calls order.RaiseCreatedEvent(). This two-step pattern is intentional.

Business methods — enforced through the aggregate only

// AddItem validates, creates the child, adds to internal list
public OrderItem AddItem(string productName, int quantity, decimal unitPrice, DateTime createdAt)
{
    var item = OrderItem.Create(Id, productName, quantity, unitPrice, createdAt);
    _items.Add(item);
    UpdatedAt = createdAt;
    return item;
}

// RemoveItem guards against missing or already-inactive items
public void RemoveItem(int itemId, DateTime updatedAt)
{
    var item = _items.FirstOrDefault(i => i.Id == itemId)
        ?? throw new DomainException($"OrderItem '{itemId}' not found.");

    if (!item.IsActive)
        throw new DomainException($"OrderItem '{itemId}' is already inactive.");

    item.Deactivate(updatedAt);     // sets IsActive=false
    UpdatedAt = updatedAt;
    AddDomainEvent(new OrderItemRemovedEvent(Id, itemId, updatedAt));
}

OrderItem.Create() is internal static — only code inside the Domain assembly can call it. Handlers in the Application layer must go through order.AddItem(). This ensures every item creation passes Order's business rules.

Reconstitute — read-side reconstruction

// Used ONLY in OrderReadRepository — bypasses all invariants
public static Order Reconstitute(
    int id, string customerName, DateTime orderDate, bool isActive,
    Guid createdBy, DateTime createdAt, Guid updatedBy, DateTime updatedAt,
    IEnumerable<OrderItem> items)
{
    var order = new Order { Id=id, CustomerName=customerName, ... };
    order._items.AddRange(items);
    return order;
}

Reading an order from the database via Dapper produces raw column data. Reconstitute reassembles the aggregate without running any validation (the data was already valid when it was written). This is the CQRS read-side.

Domain Exceptions

public class  DomainException        : Exception     { ... }  // base — maps to HTTP 422

When the domain throws a DomainException, the GlobalExceptionFilter in the Api layer catches it and returns HTTP 422. OrderNotFoundException is a special subtype that maps to 404 specifically because not finding a resource is the client's concern, not a business rule violation.

Application Layer — TemplateMs.Application

The use-case ring. References only Domain. Never references Infrastructure. All "what the system can do" lives here. All "how the system does it" stays in Infrastructure.

Why records? Commands are messages — they represent an intent at a point in time. Making them record gives structural equality (two commands with the same data are equal), immutability (no mutation after creation), and with expressions for easy test cloning.

Queries — read-only, no side effects

// The entire query type — just the Id needed to retrieve an order
public sealed record GetOrderQuery(int OrderId);

Queries carry only what is needed to identify the data. They never carry data that would mutate state. The handler returns a DTO directly from the read database — it never loads an aggregate from the write repository.

Handlers — the use-case logic

WolverineFX discovers handlers by convention: a sealed class ending in "Handler" with a Handle() method. No interface required.

CreateOrderCommandHandler — the most complete example

public sealed class CreateOrderCommandHandler
{
    // Constructor injection — Wolverine resolves from DI
    public CreateOrderCommandHandler(
        IOrderWriteRepository          writeRepository,
        IOrderItemWriteRepository      itemWriteRepository,
        IOrderItemAttributeWriteRepository attributeWriteRepository,
        IUnitOfWork                    unitOfWork,
        IDateTimeProvider              dateTimeProvider) { ... }

    // Return type → IMessageBus.InvokeAsync<OrderDto>() at the call site
    public async Task<OrderDto> Handle(CreateOrderCommand command, CancellationToken ct)
    {
        var now   = _dateTimeProvider.UtcNow;
        var order = Order.Create(command.CustomerName, command.OrderDate, now);

        _unitOfWork.RegisterAggregate(order);          // track for domain event dispatch
        await _writeRepository.AddAsync(order, ct);      // INSERT + assigns order.Id

        foreach (var itemData in command.Items ?? [])
        {
            var item = order.AddItem(itemData.ProductName, itemData.Quantity, itemData.UnitPrice, now);
            await _itemWriteRepository.AddAsync(item, order.Id, ct);
            order.RaiseItemAddedEvent(item);   // now item.Id is set by the repository

            foreach (var attrData in itemData.Attributes ?? [])
            {
                var attr = item.AddAttribute(attrData.AttributeName, attrData.AttributeValue, now);
                await _attributeWriteRepository.AddAsync(attr, item.Id, ct);
                order.RaiseAttributeAddedEvent(item.Id, attr);
            }
        }

        await _unitOfWork.CommitAsync(ct);    // SQL COMMIT + dispatch domain events
        return OrderMapper.ToDto(order);
    }
}
🔑

The two-pass event raise pattern: AddItem() creates the item and adds it to the aggregate's in-memory list. The repository's AddAsync INSERTs it and sets item.Id from OUTPUT INSERTED.Id. Only then does the handler call RaiseItemAddedEvent(item) — because the event payload needs a valid item.Id.

AddOrderItemCommandHandler — loads existing aggregate first

public async Task<OrderItemDto> Handle(AddOrderItemCommand command, CancellationToken ct)
{
    // Load the WRITE-SIDE aggregate (fully reconstituted with items + attrs)
    var order = await _readRepository.GetAggregateByIdAsync(command.OrderId, ct)
        ?? throw new OrderNotFoundException(command.OrderId);

    var now  = _dateTimeProvider.UtcNow;
    var item = order.AddItem(command.ProductName, command.Quantity, command.UnitPrice, now);

    _unitOfWork.RegisterAggregate(order);
    await _itemWriteRepository.AddAsync(item, order.Id, ct);
    order.RaiseItemAddedEvent(item);
    await _unitOfWork.CommitAsync(ct);

    return OrderMapper.ToItemDto(item);
}

Handlers that modify an existing aggregate must load it first using GetAggregateByIdAsync (which returns a fully-hydrated Order with all items and attributes). This is the write side read — the aggregate is loaded so its business methods can guard invariants.

Validators — FluentValidation, Application layer only

public sealed class CreateOrderCommandValidator : AbstractValidator<CreateOrderCommand>
{
    public CreateOrderCommandValidator()
    {
        RuleFor(x => x.CustomerName).NotEmpty().WithMessage("CustomerName is required.");
        RuleFor(x => x.OrderDate).NotEmpty().WithMessage("OrderDate is required.");

        RuleForEach(x => x.Items).ChildRules(item => {
            item.RuleFor(i => i.ProductName).NotEmpty();
            item.RuleFor(i => i.Quantity).GreaterThan(0);
            item.RuleFor(i => i.UnitPrice).GreaterThanOrEqualTo(0m);
        });
    }
}

Validators enforce input validity (is the HTTP request well-formed?). Domain exceptions enforce business invariants (does the rule make sense for this aggregate?). These are different concerns at different layers.

Middleware Behaviors — Wolverine pipeline

Wolverine middleware are plain classes with static or instance methods named Before, After, Finally, OnException, or ExecuteAsync. They run around every handler that Wolverine processes.

LoggingBehavior

public sealed class LoggingBehavior
{
    // Runs BEFORE the handler
    public static void Before(Envelope envelope, ILogger<LoggingBehavior> logger) =>
        logger.LogInformation("Handling {MessageType} id={MessageId}",
            envelope.MessageType, envelope.Id);

    // Runs AFTER successful handler
    public static void After(Envelope envelope, ILogger<LoggingBehavior> logger) =>
        logger.LogInformation("Handled {MessageType} id={MessageId}",
            envelope.MessageType, envelope.Id);

    // Runs when an exception is thrown
    public static void OnException(Exception ex, Envelope envelope, ILogger logger) =>
        logger.LogError(ex, "Failed {MessageType} id={MessageId}",
            envelope.MessageType, envelope.Id);
}

ValidationBehavior

public sealed class ValidationBehavior
{
    // ExecuteAsync wraps the handler — runs before and after
    public static async Task ExecuteAsync<T>(
        T message,
        IValidator<T>? validator,   // null if no validator registered for this type
        Func<Task> next,
        CancellationToken ct) where T : notnull
    {
        if (validator is not null)
        {
            var result = await validator.ValidateAsync(message, ct);
            if (!result.IsValid)
                throw new ValidationException(result.Errors);
        }
        await next();   // proceed to handler
    }
}

TransactionBehavior

public sealed class TransactionBehavior
{
    public static async Task ExecuteAsync(
        IUnitOfWork unitOfWork,
        Func<Task>  next,
        CancellationToken ct)
    {
        await next();                          // run the handler
        await unitOfWork.CommitAsync(ct);      // commit if handler didn't already
    }
}
💡

TransactionBehavior is a safety net. Handlers like CreateOrderCommandHandler call CommitAsync explicitly — they need to commit before building the return DTO. The TransactionBehavior calls it again but the second call is harmless because the transaction was already committed.

Manual Mapper — no reflection, zero magic

public static class OrderMapper
{
    public static OrderDto ToDto(Order order) =>
        new(
            order.Id,
            order.CustomerName,
            order.OrderDate,
            order.IsActive,
            order.Items.Select(ToItemDto).ToList().AsReadOnly(),

Infrastructure Layer — TemplateMs.Infrastructure

The outer ring. Implements all Application interfaces. References Application, Domain, and Sql. Must never reference TemplateMs.Api.

Connection Factories — separating read and write concerns

public sealed class CommandDbConnectionFactory : ICommandDbConnectionFactory
{
    private readonly string _connectionString;
    public CommandDbConnectionFactory(IOptions<InfrastructureOptions> options) =>
        _connectionString = options.Value.CommandConnectionString;

    public IDbConnection CreateConnection()
    {
        var conn = new SqlConnection(_connectionString);
        conn.Open();          // opens synchronously — called from UoW constructor
        return conn;
    }
}

// QueryDbConnectionFactory is identical but uses QueryConnectionString

Two factories — two connection strings. Both point to the same SQL Server in development. In production you can point the query factory to a read replica. Zero code changes are required — it's purely a configuration change.

Unit of Work — the transaction coordinator

This is the most important Infrastructure type to understand. It coordinates the SQL transaction, domain event dispatch, and outbox persistence.

public sealed class DapperUnitOfWork : IUnitOfWork, IDisposable, IAsyncDisposable
{
    private readonly List<AggregateRoot> _trackedAggregates = [];
    private readonly IDomainEventDispatcher _dispatcher;

    // Opens connection + begins transaction in the constructor
    public DapperUnitOfWork(ICommandDbConnectionFactory factory, ...)
    {
        Connection  = factory.CreateConnection();
        Transaction = Connection.BeginTransaction(IsolationLevel.ReadCommitted);
    }

    // Exposed to write repositories — they share this connection + transaction
    public IDbConnection  Connection  { get; }
    public IDbTransaction Transaction { get; }

    public void RegisterAggregate(AggregateRoot agg) => _trackedAggregates.Add(agg);

    public async Task QueueOutboxMessageAsync(string messageType, string payload, ...)
    {
        // INSERT happens inside the SAME transaction as the business data
        await Connection.ExecuteAsync(OutboxSql.Insert,
            new { Id = Guid.NewGuid(), MessageType = messageType, Payload = payload, ... },
            Transaction);
    }

    public async Task CommitAsync(...)
    {
        Transaction.Commit();                     // 1. commit all SQL writes atomically
        var aggregates = _trackedAggregates.ToList();
        _trackedAggregates.Clear();
        await _dispatcher.DispatchAsync(aggregates, ct); // 2. dispatch domain events
    }
}
🔑

The ordering in CommitAsync matters. SQL Transaction.Commit() happens first. Domain events are dispatched only after the data is safely committed. If event dispatch fails, the data is still saved — the worst case is a missed domain event, not a lost order.

Repositories — write-side vs read-side

Write repository — shares the UoW transaction

public sealed class OrderWriteRepository : IOrderWriteRepository
{
    private readonly DapperUnitOfWork     _unitOfWork;   // concrete type — shares tx
    private readonly ICurrentUserProvider _currentUser;

    public async Task AddAsync(Order order, CancellationToken ct)
    {
        var userId = _currentUser.UserId;

        // ExecuteScalarAsync returns the IDENTITY value via OUTPUT INSERTED.Id
        var id = await _unitOfWork.Connection.ExecuteScalarAsync<int>(
            OrderCommandSql.Insert,
            new { order.CustomerName, order.OrderDate, order.IsActive,
                  CreatedBy = userId, order.CreatedAt,
                  UpdatedBy = userId, order.UpdatedAt },
            _unitOfWork.Transaction);    // participates in the shared tx

        order.Id        = id;            // hydrate the aggregate with DB-assigned Id
        order.CreatedBy = userId;
        order.UpdatedBy = userId;
        order.RaiseCreatedEvent(order.CreatedAt);  // safe now — Id is assigned
    }
}

Read repository — independent connection, no transaction

public sealed class OrderReadRepository : IOrderReadRepository
{
    private readonly IQueryDbConnectionFactory _queryFactory;

    public async Task<OrderDto?> GetByIdAsync(int orderId, CancellationToken ct)
    {
        using IDbConnection conn = _queryFactory.CreateConnection();  // own connection

        // Multi-result-set: Grid 1 = Order, Grid 2 = OrderItems, Grid 3 = OrderItemAttributes
        using var multi = await conn.QueryMultipleAsync(OrderQuerySql.GetById, new { Id = orderId });

        var orderRow = await multi.ReadSingleOrDefaultAsync<OrderRow>();
        if (orderRow is null) return null;

        var itemRows = (await multi.ReadAsync<OrderItemRow>()).ToList();
        var attrRows = (await multi.ReadAsync<OrderItemAttributeRow>()).ToList();

        return MapToDto(orderRow, itemRows, attrRows);
    }
}

The single SQL call to OrderQuerySql.GetById returns three grids in one round-trip — the order header, all its items, and all attributes for all items. Dapper's QueryMultiple reads them sequentially. This avoids N+1 queries entirely.

Handler commits transaction │ OutboxMessages INSERT is inside this transaction ▼ SQL Transaction.Commit() │ Order row + OutboxMessages row — both committed atomically ▼ OutboxProcessor (BackgroundService) │ polls every 5 000ms │ SELECT TOP 50 FROM OutboxMessages WHERE ProcessedAt IS NULL ▼ For each OutboxRecord: │ ActiveMqPublisher.PublishAsync(OutboxEnvelope) │ → success: UPDATE ProcessedAt = now │ → failure: UPDATE Error = ex.Message ▼ ActiveMQ: order.events queue

What if the process crashes between commit and publish? The outbox record has ProcessedAt = NULL and Error = NULL. On next startup the OutboxProcessor will pick it up and retry. This is at-least-once delivery — consumers must be idempotent (use the EventId for deduplication).

ActiveMQ Publisher

public sealed class ActiveMqPublisher : IMessageBusPublisher, IAsyncDisposable
{
    public async Task PublishAsync<T>(T message, CancellationToken ct) where T : class
    {
        var factory    = new ConnectionFactory(_config.BrokerUrl);
        using var conn    = await Task.Run(() => factory.CreateConnection(_config.Username, _config.Password));
        conn.Start();

        using var session  = conn.CreateSession(AcknowledgementMode.AutoAcknowledge);
        var destination = session.GetQueue(_config.OrderEventsQueue);
        using var producer = session.CreateProducer(destination);

        var json       = JsonSerializer.Serialize(message);
        var nmsMessage = session.CreateTextMessage(json);
        nmsMessage.Properties.SetString("MessageType", typeof(T).FullName);
        producer.Send(nmsMessage);
    }
}

public async Task InvokeAsync(HttpContext context)
{
    // Read from incoming header, or generate a new GUID
    var correlationId = context.Request.Headers["X-Correlation-Id"].FirstOrDefault()
                        ?? Guid.NewGuid().ToString();

    // Store in HttpContext so GlobalExceptionFilter and other middleware can read it
    context.Items["CorrelationId"] = correlationId;

    // Echo back to the client on every response
    context.Response.Headers["X-Correlation-Id"] = correlationId;

    await _next(context);

Error Handling — GlobalExceptionFilter

public sealed class GlobalExceptionFilter : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(HttpContext ctx, Exception ex, CancellationToken ct)
    {
        var correlationId = ctx.Items["CorrelationId"]?.ToString() ?? "";
        _logger.LogError(ex, "CorrelationId={CorrelationId}", correlationId);

        var (status, title, _) = ex switch
        {
            ValidationException   => (400, "Validation Failure",     ...),
            OrderNotFoundException => (404, "Resource Not Found",     ...),
            DomainException       => (422, "Business Rule Violation", ...),
            _                       => (500, "Internal Server Error",  ...)
        };

        var problem = new ProblemDetails { Status=status, Title=title, Detail=ex.Message };
        problem.Extensions["correlationId"] = correlationId;
        if (ex is ValidationException ve)
            problem.Extensions["errors"] = ve.Errors;

        ctx.Response.StatusCode = status;
        await ctx.Response.WriteAsJsonAsync(problem, ct);
        return true;   // handled — don't pass to next handler
    }
}

Full Flow: Create Order End-to-End

  1. HTTP Request arrives

    POST /api/orders with JSON body. CorrelationIdMiddleware runs first — reads or generates X-Correlation-Id and stores it in HttpContext.Items.

  2. Controller maps to command

    OrderController.Create deserialises CreateOrderRequest → builds CreateOrderCommand (sealed record). Calls IMessageBus.InvokeAsync<OrderDto>(command).

  3. Wolverine middleware — Logging

    LoggingBehavior.Before logs "Handling CreateOrderCommand id=..."

  4. Wolverine middleware — Validation

    ValidationBehavior.ExecuteAsync calls CreateOrderCommandValidator.ValidateAsync. If validation fails → throws ValidationException → caught by GlobalExceptionFilter → returns HTTP 400.

  5. Handler executes

    CreateOrderCommandHandler.Handle: calls Order.Create(), registers aggregate, calls OrderWriteRepository.AddAsync() (Dapper INSERT + OUTPUT INSERTED.Id), iterates items and attributes, builds the aggregate in memory.

  6. UoW CommitAsync

    DapperUnitOfWork.CommitAsync(): calls Transaction.Commit() — all INSERTs are atomically durable. Then calls IDomainEventDispatcher.DispatchAsync(trackedAggregates).

  7. Domain event dispatch

    WolverineEventForwarders.DispatchAsync calls IMessageBus.PublishAsync(OrderCreatedEvent). Wolverine routes this to OrderDomainEventHandler.

  8. Domain event handler → outbox

    OrderDomainEventHandler.Handle builds OrderCreatedIntegrationEvent, serialises to JSON, calls IUnitOfWork.QueueOutboxMessageAsync (INSERT into OutboxMessages), then calls CommitAsync again (commits this second transaction).

  9. Controller returns HTTP 201

    Handler returns OrderDto. Controller maps via OrderResponse.FromDto(dto). Returns CreatedAtAction — HTTP 201 with Location: /api/orders/42 and JSON body.

  10. OutboxProcessor (async, background)

    Polls every 5s. Reads unprocessed rows. Calls ActiveMqPublisher.PublishAsync(OutboxEnvelope) → ActiveMQ order.events queue. Marks row as processed.

Full Flow: Domain Event → Integration Event

Order.Create() / AddItem() / etc. └── AddDomainEvent(OrderCreatedEvent) ← stored in _domainEvents list DapperUnitOfWork.CommitAsync() ├── Transaction.Commit() ← all SQL writes are now durable └── IDomainEventDispatcher.DispatchAsync([order]) WolverineEventForwarders.DispatchAsync └── IMessageBus.PublishAsync(OrderCreatedEvent) ← re-enters Wolverine (in-process, same thread) Wolverine routes → OrderDomainEventHandler.Handle(OrderCreatedEvent) ├── builds OrderCreatedIntegrationEvent { OrderId, CustomerName, ... } ├── JsonSerializer.Serialize(integrationEvent) → JSON string ├── IUnitOfWork.QueueOutboxMessageAsync("...IntegrationEvent", json) │ └── INSERT INTO OutboxMessages (inside new transaction) └── IUnitOfWork.CommitAsync() ← commits the outbox INSERT OutboxProcessor.ExecuteAsync() — runs every 5 000ms ├── OutboxStorage.GetUnprocessedAsync() │ └── SELECT TOP 50 WHERE ProcessedAt IS NULL ORDER BY CreatedAt ├── foreach record: │ ├── ActiveMqPublisher.PublishAsync(new OutboxEnvelope(...)) │ │ ├── ConnectionFactory(BrokerUrl).CreateConnection() │ │ ├── session.CreateProducer(queue) │ │ └── producer.Send(TextMessage(json)) │ └── OutboxStorage.MarkProcessedAsync(record.Id) └── Task.Delay(5000ms)

Use Product as the example. Follow every step in this exact order.

  1. Domain entity

    Create src/core/TemplateMs.Domain/Entities/Product.cs — sealed class Product : BaseAuditableEntity with factory method, private setters on business properties, business methods that throw DomainException.
